ExcedentMarket enforces a strict three-role model built on top of [spatie/laravel-permission](https://github.com/spatie/laravel-permission) and [filament-shield](https://github.com/bezhanSalleh/filament-shield). Every authenticated session belongs to exactly one role, and that role determines which Filament panel the user lands on, which resources they can read or write, and which marketplace actions are available to them. The separation reflects the real-world circular economy chain mandated by **Ley N.° 3956/2009**: industrial waste generators publish surplus lots, recyclers bid on them, and the platform administrator oversees compliance without participating in trading.

## Login flow

All three roles share a single login form at `/login`, rendered by the Inertia + React frontend. After successful authentication, the session is regenerated and the user is redirected to `/portal`, which resolves the correct panel based on the assigned role:

```php
// web/routes/web.php
Route::get('/portal', function () {
    $user = auth()->user();

    return match (true) {
        $user->hasRole('admin')      => redirect('/admin'),
        $user->hasRole('generador')  => redirect('/generador'),
        $user->hasRole('reciclador') => redirect('/reciclador'),
        default                      => redirect('/'),
    };
})->name('portal');
```

Each Filament panel also exposes its own dedicated login URL for direct access:

| Role | Panel URL | Direct login |
|---|---|---|
| Admin | `/admin` | `/admin/login` |
| Generador | `/generador` | `/generador/login` |
| Reciclador | `/reciclador` | `/reciclador/login` |

The `LoginController` uses a uniform error message regardless of whether the email or password is wrong, preventing account-enumeration attacks (relevant under **Ley N.° 7.593** on personal data protection):

```php
// web/app/Http/Controllers/Auth/LoginController.php
private const CREDENCIALES_INVALIDAS =
    'Las credenciales no son validas. Revisa el correo y la contrasena.';

public function store(Request $request): RedirectResponse
{
    $credentials = $request->validate([
        'email'    => ['required', 'email'],
        'password' => ['required'],
    ]);

    if (Auth::attempt($credentials, $request->boolean('remember'))) {
        $request->session()->regenerate();
        return redirect()->intended('/portal');
    }

    app(DeteccionIncidentes::class)->loginFallido(
        $request->input('email'),
        $request->ip()
    );

    return back()
        ->withErrors(['email' => self::CREDENCIALES_INVALIDAS])
        ->withInput($request->only('email'));
}
```

<Note>
  Failed login attempts are recorded by `DeteccionIncidentes`. When a brute-force threshold is exceeded from a single IP, a security incident is opened automatically in the `IncidenteSeguridad` log.
</Note>

## Registration

Only **Generador** and **Reciclador** users can self-register via `GET /register` and `POST /register`. The **Admin** account is created exclusively by the database seeder and cannot be registered through the public form.

```
POST /register   → creates generador or reciclador account
POST /login      → authenticates and redirects to /portal
GET  /portal     → role-based redirect to /admin | /generador | /reciclador
```

## Permission system

Permissions are generated by filament-shield using Filament's resource and page classes as the canonical permission source. The `shield:generate` command must be run **before** `db:seed` so that the roles created by the seeder already have the correct permission entries in the database.

```bash
php artisan shield:generate --all
php artisan db:seed
```

<Warning>
  Running `db:seed` before `shield:generate` will create roles without permissions. Resources like **Mis Lotes** in the Generador panel will silently disappear from the navigation menu. Always run `shield:generate` first, or re-run both in order after any policy change.
</Warning>

Each panel uses `canViewAny()`, `canView()`, `canEdit()`, and `canCreate()` overrides in its resource classes to enforce row-level isolation. For example, `LotePublicadoResource` in the Generador panel scopes every query to `generador_id = auth()->user()->empresa_id`, so generators can never see another company's lots regardless of their Shield permissions.

## Privacy consent

After login, the middleware `VerificarConsentimientoPrivacidad` checks whether the user's accepted policy version matches the currently active version. If not, they are redirected to `/privacidad/aceptar` before reaching their panel. This flow implements the re-consent requirement of **Ley N.° 7.593**.
